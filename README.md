# Hangly Desktop Companion

A Hangly-inspired desktop companion application for Windows (macOS planned), built on **Electron + React + TypeScript + Vite**, with **Matter.js** for physics and **PixiJS** for rendering, packaged with **Electron Forge**. A bundled star charm hangs from a rope; it can be grabbed, dragged, and released to swing.

## Requirements

- Node.js 22.12+ (LTS recommended) and npm
- Windows 10/11 for packaging Windows installers

## Getting started

```bash
npm install
npm run dev
```

`npm run dev` (alias of `npm start`) launches the app with Vite HMR: edits to the renderer hot-reload, and main-process changes restart the app automatically.

## Physics & rendering

The hanging charm is simulated with **Matter.js** and drawn with **PixiJS**:

- `src/renderer/physics/config.ts` — every tuning value (rope length, gravity, damping, solver iterations)
- `src/renderer/physics/scene.ts` — the physics world: a static anchor, a rope of chained bodies, and the charm. Pure physics, no DOM, so it can run headless in tests.
- `src/renderer/physics/view.ts` — PixiJS drawing: smoothed rope curve, anchor pin, and the charm sprite
- `src/renderer/charms/` — the visual asset system: `types.ts` (the `CharmAsset` model) and `registry.ts` (built-in assets)
- `src/renderer/CharmSimulation.tsx` — the single loop tying physics and rendering together

How they connect:

1. Pixi's ticker reports the real elapsed frame delta.
2. That delta feeds a fixed-timestep accumulator, and the Matter engine is stepped at a constant 60 Hz (`fixedTimestepMs`), up to `maxSubSteps` times per frame.
3. After stepping, the pose is interpolated between the previous and current physics state using the leftover accumulator fraction, so motion is smooth on any refresh rate (including 120/144 Hz displays).
4. Pixi redraws the rope as a smoothed curve through those interpolated points and moves/rotates the charm graphic. The renderer only reads physics — it never writes back into the world.

Stability details: long frame hiccups are clamped (`maxFrameDeltaMs`) so the simulation can't "spiral" after a stall, rope links have collisions disabled (the rope is a pure constraint chain), and the charm is attached by a constraint that cannot detach — it cannot fall off the rope. Damping comes from `charmFrictionAir`, `segmentFrictionAir`, and constraint `damping`, so the swing decays to rest instead of drifting forever.

### Charm assets

What the charm *looks like* lives entirely in `src/renderer/charms/`, separate from what it *is* physically:

- `types.ts` — the `CharmAsset` model (id, name, type, texture source, size, pivot, rope anchor, body diameter) plus a validator that runs on registration.
- `registry.ts` — the built-in assets and the lookup API: `getDefaultCharmAsset()` and `getCharmAsset(id)`. Unknown ids fall back to the default, so a bad id can never break the overlay.
- `assets/charms/star.png` — the built-in "Lucky Star" (original artwork, generated by `node scripts/gen-charm-asset.mjs`; the PNG is committed).

Physics and visuals stay independent: the texture may be any size, and the view scales it so `asset.bodyDiameter` texture pixels equal the physics body's fixed diameter (`charmRadius * 2`). Artwork may overhang the physical circle (the star's tips do) without touching the simulation — swapping the asset never changes a single physics value.

Assets are bundled, never remote: Vite inlines the small PNG as a `data:` URI at build time (`assetsInlineLimit`), which satisfies the strict CSP. The view also avoids `Assets.load()` — Pixi's asset loader spawns blob-URL workers that a CSP without `worker-src` blocks — and instead decodes with `new Image()` + `Texture.from()` on the main thread.

To add a charm: drop a PNG in `src/renderer/assets/charms/`, import it in `registry.ts`, and append a `CharmAsset` entry.

### Tuning

| Value | Default | Meaning |
| --- | --- | --- |
| `ropeLength` / `segmentLength` | 156 / 20 | Rope rest length in px, and target link size |
| `gravityX` / `gravityY` / `gravityScale` | 0 / 1 / 0.001 | Gravity strength |
| `charmFrictionAir` | 0.016 | Charm drag — how fast the swing dies out |
| `segmentFrictionAir` | 0.02 | Rope drag |
| `constraintStiffness` / `constraintDamping` | 1 / 0.02 | Rope rigidity and energy loss |
| `constraintIterations` | 12 | Solver passes — how taut the rope stays under load |
| `initialSwingAngle` | 0.55 | Launch angle of the rope (radians) |
| `dragStiffness` / `dragDamping` | 0.35 / 0.1 | How tightly the charm follows the pointer |
| `dragFollowSpeed` | 1.5 px/ms | Max speed the drag point chases the pointer |
| `dragMaxSpeed` | 36 px/step | Safety cap on charm speed while dragging |

Values can be overridden per scene, e.g. `createCharmScene(width, height, { ropeLength: 220, charmFrictionAir: 0.03 })`.

## Interaction: grabbing and dragging

The charm is the only interactive object in the overlay. Its Pixi `Sprite` has
`eventMode: 'static'` and a circular hit area; the rope, the rest of the canvas and
the hint panel (`pointer-events: none`) all ignore pointers.

- **Pointer events** come from Pixi's federated system (`pointerover`, `pointerout`,
  `pointerdown`, `pointermove`, `pointerup`, `pointerupoutside`). On grab, the canvas
  element takes native `setPointerCapture`, so moves and the release keep arriving even
  when the pointer leaves the charm — or the window. Window blur and `pointercancel`
  end a drag, so the charm can never get stuck in a grabbed state.
- **Coordinates**: Matter world units are CSS pixels. The view converts client
  coordinates with `stage.toLocal()`, and Pixi's `autoDensity`/`resolution` handle the
  device pixel ratio inside the renderer — so physics is DPR-independent while the
  canvas stays crisp on scaled displays.
- **Physics**: `beginDrag()` adds one temporary Matter `Constraint` (`pointA` = drag
  point in world space, `bodyB` = charm, `pointB` = the grab offset in body space) — the
  same technique Matter's own MouseConstraint uses. The solver moves the charm; the
  renderer never writes positions. `endDrag()` removes the constraint and the charm
  keeps its velocity, so it swings away naturally and settles.
- **Force limits**: the drag point chases the pointer at `dragFollowSpeed` (bounded per
  physics step) and is projected into the rope's reachable disc, so a pointer teleport
  or dragging past the rope's length cannot yank the rope (a 200px teleport moves the
  charm at most one chase step, and rope stretch stays around 2-8% instead of 80%+).
  `dragMaxSpeed` is a final safety valve against explosive velocities.
- **Feedback**: the cursor switches to `grab`/`grabbing`, and the charm eases to a
  slightly larger scale with a highlight ring while hovered or grabbed — all animated
  inside the existing render loop, no extra timers.

`tests/physics.test.mjs` covers the interaction headlessly (grab/release lifecycle,
repeated clicks, fast and out-of-bounds drags, release-outside, inward drags, anchor
and rope integrity, NaN checks); `tests/charms.test.mjs` covers the asset registry
(default lookup, unknown-id fallback, dimension/pivot validation, and that changing
the asset never changes the physics config). `npm test` bundles the physics scene and
config with esbuild first so Node can run them.

In development, the console logs a one-shot `[charm]` report after a few seconds (rope stretch and charm speed) so the simulation can be checked without watching the window.

## Security model

The window is configured with hardened Electron defaults:

- `contextIsolation: true` and `nodeIntegration: false` — the renderer has no direct Node access
- `sandbox: true` for the renderer
- A minimal, typed preload API (`window.hangly`) is the **only** bridge between processes
- A restrictive Content-Security-Policy in `index.html`
- `window.open` / external navigation is redirected to the OS browser via `shell.openExternal`
- At package time, Forge fuses disable `RunAsNode`, Node CLI inspect flags, and `NODE_OPTIONS`, and enable ASAR integrity validation
